## Конфигурация агентов
  
Для каждой конфигурации записан отдельный PCAP-файл. В ходе одного запуска агента выполнен одинаковый сценарий активности, включающий выполнение команд, передачу файлов и изменение интервала обращений к серверу. Каждый запуск сопровождается установлением нескольких TCP-соединений.

Конфигураций агента будет 5 шт: Сборка A, Сборка B, Сборка C, Сборка D, Сборка E

Сходство:

| Параметр                         | Значение                          | На что влияет                                                          |
| -------------------------------- | --------------------------------- | ---------------------------------------------------------------------- |
| ОС                               | Linux                             |                                                                        |
| Agent                            | Medusa                            |                                                                        |
| https_check                      | yes                               | проверяет сертификат при HTTPS. При http не влияет на обмен            |
| obfuscate_script                 | no                                | меняет представление кода агента на диске                              |
| output                           | py                                | формат выходного файла                                                 |
| python_version                   | Python 3.8                        | вариант кода в Medusa                                                  |
| use_non_default_cryptography_lib | no                                | выбирает собственную реализацию криптографии вместо внешней библиотеки |
| C2 Profile                       | http                              |                                                                        |

| Начальный jitter                 | 0                                 |                                                                        |

### Конфигурация сборок:

Сборка A: шифрование отключено, encrypted_exchange_check = False. Дамп a-http.pcap использовал для разбора сообщений без AES.
Сборка B: включено aes256_hmac, encrypted_exchange_check = False. На b-aes.pcap проверял, какие признаки сохраняются при шифровании.
Сборка C: включено AES, пути изменены на /lab_get и /lab_post. На c-uri.pcap проверял влияние изменения URI.
Сборка D: включено AES, User-Agent заменён на Mozilla/5.0. На d-ua.pcap проверял влияние изменения этого заголовка.
Сборка E: включено AES, encrypted_exchange_check = True. Дамп e-exchange.pcap использовал для проверки этого параметра. Фактический обмен ключами не подтвердился, поскольку соответствующая настройка в коде дальше не используется.

Для каждой сборки используется одинаковый сценарий активности. Трафик записывается в отдельный PCAP с момента запуска агента до завершения его работы. Остальные параметры, кроме указанных различий, сохраняются одинаковыми.
При проверке кода выяснил, что параметр ExchChk сохраняется в настройках, но дальше не используется. Поэтому фактический обмен ключами в E не подтвердился. Этот дамп рассматриваю как дополнительный запуск с AES.

# Разработка сигнатур

## Исследование базового дампа A

Исследование начал с файла a-http.pcap. В конфигурации A шифрование сообщений отключено, поэтому на этом дампе проще разобраться в структуре обмена между агентом и сервером. Сначала решил определить назначение запросов и ответов, а затем искать признаки, которые можно использовать в сигнатурах. И применил фильтр http.request:
![](<images/1.png>)

В списке остались HTTP-запросы агента. Среди них встречаются `POST /data` и `GET /index?q=...`. В GET-запросах данные передаются через параметр q, а в POST находятся в теле запроса. При этом даже без AES содержимое сообщений не выглядит как обычный JSON: оно закодировано в Base64.

Для подробного просмотра выбрал первый POST /data и открыл Follow, TCP Stream. Так можно увидеть запрос и ответ целиком, даже если они были переданы несколькими TCP пакетами.![](<images/2.png>)
В HTTP-заголовках видны адрес сервера, User-Agent, тип и длина содержимого. Эти поля пока рассматриваю как потенциальные признаки. Например, URI и User-Agent заданы в конфигурации агента и могут меняться, поэтому их пригодность нужно проверить на остальных дампах.

### Запрос регистрации агента

В строке фильтров ввел tcp.stream eq 0, затем нажал на первый пакет, follow и TCP Stream. В первом TCP потоке находится HTTP-запрос:
![](<images/4.png>)Этот же запрос в CyberChef:
![](<images/5.png>)
Значение action: checkin определяет назначение сообщения: агент регистрируется на сервере. Вместе с ним передаются сведения о системе, пользователе, имени узла и процессе агента. UUID перед JSON совпадает со значением поля uuid внутри запроса.
Поле ip содержит 127.0.1.1, хотя в IP заголовках пакетов адрес агента равен 192.168.64.5. Значит, сведения, которые агент сообщает о себе, нужно отличать от адресов самого сетевого соединения. В коде Medusa значение этого поля получается через разрешение имени локального узла.
Также заметил несоответствие между architecture: x64 и строкой ОС, содержащей arm64. В данной реализации агент определяет разрядность Python, поэтому значение x64 здесь не подтверждает использование архитектуры x86-64.
Для будущей сигнатуры отметил несколько возможных признаков: метод POST, Base64 кодирование тела, UUID перед JSON и сочетание полей регистрационного сообщения. Однако сам POST и отдельные поля вроде user или pid встречаются и в легитимных приложениях. Их нужно оценивать вместе.
Конкретные значения IP, имени пользователя, PID и UUID зависят от среды запуска, поэтому привязывать к ним обнаружение не подходит. Длина тела тоже может измениться, например из за другой длины имени узла или строки ОС.
На этом этапе определил структуру запроса регистрации. Следующим шагом нужно сравнить его с рабочими сообщениями агента: возможно, часть найденных особенностей сохраняется не только при первом подключении.
### Ответ сервера на регистрацию

Скопировал Base64 строку из тела ответа сервера и декодировал её. Получилось следующее сообщение:
![](<images/3.png>)
В начале сообщения находится UUID длиной 36 символов. Сразу после него, без отдельного разделителя, начинается JSON. Для удобства разбора представил JSON отдельно:

```
{
  "encryption_key": null,
  "action": "checkin",
  "id": "eb77c872-7660-4ebf-9d0e-57e17a0740db",
  "status": "success",
  "decryption_key": null
}
```

Значение checkin указывает, что сообщение относится к регистрации агента. Поле status содержит success, то есть сервер принял регистрацию. В поле id сервер возвращает UUID callback, который агент использует в последующих сообщениях.
Поля ключей в этом ответе равны null. Это соответствует настройкам конфигурации A, в которой AES отключён. Сам JSON удалось прочитать после одного Base64 декодирования, без использования ключа.
На этом примере видно, что нужно различать кодирование и шифрование. В A Base64 меняет представление сообщения, но не скрывает его содержимое от анализа.
Для дальнейшего исследования отметил структуру сообщения: UUID перед JSON и набор полей ответа на регистрацию. Конкретные значения UUID зависят от сборки и зарегистрированного callback, поэтому использовать их как постоянные значения в сигнатуре не подходит.

### Выбор признаков для первого правила

После разбора опросов решил попробовать написать первое правило. Привязываться к IP-адресам и конкретному UUID не стал: они относятся к моему запуску агента. Пути /index и /data тоже можно изменить в настройках, поэтому опираться на них не буду.
В запросе заданий после декодирования Base64 находятся action: get_tasking и tasking_size: -1. Агент отправляет такое сообщение и тогда, когда задания есть и когда их нет. В первом правиле попробую декодировать значение параметра q и искать эти поля. Затем проверю его на a-http.pcap в Dalton. Для сборок с AES понадобится другой подход, поскольку после Base64 декодирования JSON остаётся зашифрованным.

### Первое правило

По вышеописанным признакам составил правило для обнаружения запросов заданий:

```
alert http any any -> any any (msg:"Mythic HTTP get_tasking"; flow:established, to_server; http.uri; content:"?q="; base64_decode:bytes 256,relative; base64_data; content:"|22|action|22|: |22|get_tasking|22|"; content:"|22|tasking_size|22|: -1"; classtype:trojan-activity; sid:1; rev:1;)
```

Правило проверяет HTTP-запросы в сторону сервера. Через http.uri нахожу ?q=, после которого агент передаёт сообщение. Затем base64_decode декодирует до 256 байт. Параметр relative указывает, что декодирование начинается сразу после найденного ?q=. Через base64_data перехожу к декодированным данным и ищу сочетание "action": "get_tasking" и "tasking_size": -1.  |22| означает двойную кавычку внутри условия content. Ожидаю, что правило будет обнаруживать опросы в конфигурации A как при наличии заданий, так и без них. 
Эта версия привязана к имени параметра q. Если изменить его в настройках агента, правило может пропустить запрос.

### Проверка первого правила в Dalton

Перед запуском посчитал запросы, которые должно обнаруживать правило. Для этого применил в Wireshark фильтр http.request.method == "GET"

В нижней строке окна отображается 136. В дампе A это 136 запросов get_tasking, включая опросы без заданий и обращения, в ответ на которые сервер передал команды. Поэтому ожидаемое количество срабатываний первого правила составило 136. Затем загрузил a-http.pcap в Dalton, выбрал Suricata 8.0.7 и запустил проверку правила. Получил 136 срабатываний с sid:1.
![](<images/dalton A.png>)

Таким образом, первое правило обнаружило все опросы за заданиями в дампе A. Дальше нужно добавить обнаружение POST запросов и обмена с включённым AES.![](<images/DaltonA.png>)
### Обнаружение POST запроса

Применил в строке фильтров команду http.request.method == "POST"
![](<images/9.png>)
После применения фильтра осталось 64 запроса. При разборе сообщений выделил один запрос регистрации checkin и 63 сообщения post_response. Среди них находятся результаты команд, сообщение об ошибке и обмен при передаче файлов.
Для следующего правила выбрал сочетание `"action": "post_response"` и `"responses": [`. Эти признаки находятся в начале сообщений и сохраняются при разной активности агента.

```
alert http any any -> any any (msg:"Mythic HTTP post_response"; flow:established, to_server; http.method; content:"POST"; http.request_body; base64_decode:bytes 512; base64_data; content:"|22|action|22|: |22|post_response|22|"; content:"|22|responses|22|: ["; classtype:trojan-activity; sid:2; rev:1;)
```

Здесь проверяю метод POST, затем через http.request_body перехожу к телу запроса. Декодирование начинается с начала тела, поэтому relative не использую. Предел 512 байт выбрал с запасом для проверки начальных полей сообщения.
Для этого правила ожидаю 63 срабатывания на A. Регистрацию оно не покрывает, поскольку в ней используется другое действие - checkin.

## Выбор и отбрасывание признаков

При выборе признаков отказался от конкретных IP адресов, UUID, имени пользователя и PID. Эти значения относятся к отдельному запуску агента. Пути запросов и User-Agent тоже не стал фиксировать, поскольку они меняются в настройках. Интервал опросов не использовал, может меняться командой sleep.
Для обмена без AES выбрал поля сообщений после Base64 декодирования. Сочетание get_tasking и tasking_size позволяет обнаруживать опросы как с заданиями, так и без них. Для результатов использовал post_response и responses. Эти поля сохраняются при выполнении разных команд, ошибках и передаче файлов. Регистрацию проверяю отдельно по сочетанию checkin, uuid и architecture.
При включённом AES содержимое JSON скрыто. Для POST использовал формат UUID в начале сообщения и наличие бинарных данных после него. Для GET использовал формат UUID и длину значения параметра 176 символов, которая сохранялась в исследованных запросах заданий. Саму длину отдельно от остальных условий не использую. Если формат запроса изменится, это ограничение может привести к пропуску.
Правила для AES проверяют внешнюю структуру сообщения, но не расшифровывают его и не проверяют HMAC. Поэтому срабатывание само по себе не доказывает использование именно Medusa. Похожий формат может встретиться у другого агента или легитимного приложения.

### Доработка первого правила

В первоначальном варианте первого правила осталось фиксированное имя параметра q. Убрал эту привязку. Теперь значение параметра извлекается через pcrexform, затем после декодирования проверяются те же поля JSON.

```
alert http any any -> any any (msg:"Mythic HTTP get_tasking"; flow:established, to_server; http.method; content:"GET"; http.uri; pcrexform:"[?&][^=&]+=([A-Za-z0-9_-]+={0,2})(?:&|$)"; from_base64; content:"|22|action|22|: |22|get_tasking|22|"; content:"|22|tasking_size|22|: -1"; classtype:trojan-activity; sid:1; rev:2;)
```

### Возможные ложные срабатывания и пропуски

Ложные срабатывания возможны у приложений с похожим форматом данных. Например, четвёртое правило может обнаружить обычную передачу бинарных данных, если после Base64 декодирования перед ними находится UUID. Для пятого достаточно совпадения длины параметра и формата UUID в его начале. Поэтому эти признаки сами по себе не доказывают использование Medusa и могут встречаться у других агентов Mythic.
Пропуски возможны при изменении сообщений. Первые три правила ищут конкретные строки JSON с пробелами. Пятое зависит от длины параметра 176 символов. Первое может пропустить нужное значение, если перед ним находится другой параметр, подходящий под выражение для извлечения Base64.
При использовании HTTPS без расшифрования содержимое HTTP будет недоступно этим правилам. Также не проверялись другие транспорты и полноценный обмен ключами. В дампе E наблюдался обычный обмен с AES, поэтому считать его подтверждением обнаружения обмена ключами нельзя.
Итоговый набор обнаружил все 736 запросов агента в исследованных дампах. Отдельных правил на ответы сервера нет. Полученное покрытие относится к записанным сценариям и не гарантирует обнаружение всех вариантов работы Medusa.
